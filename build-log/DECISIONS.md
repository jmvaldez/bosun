## Deviations

- **D-1 Linux first.** Milestone M7 (Linux) folds into M1a: the `_linux.go` adapters (procs via `/proc/<pid>/stat`, termios, `notify-send` backend, tmux-flag focus) are the primary path and are built and tested first. Darwin adapters are written against the same interfaces and kept cross-building, but their live checks are deferred. Live acceptance checks marked macOS-only become `BLOCKED (macOS)`, not failures.
- **D-2 Go toolchain.** `go.mod` declares `go 1.26.0` with `toolchain go1.26.10`; `GOTOOLCHAIN=auto` fetches it into the module cache. Nothing installed system-wide. CI's `setup-go` v5 with `go-version-file: go.mod` reads only the `go` line (so it installs 1.26.0), but the `go` command it runs then honours the `toolchain` line under the default `GOTOOLCHAIN=auto` and downloads go1.26.10, so release binaries carry the stdlib security fixes.
- **D-3 tmux 3.2 minimum.** Supported floor is 3.2 (Ubuntu 22.04 apt). The generated conf gates 3.3+ features at load time (`display-popup -T` only on ≥ 3.3, via `if -F '#{>=:#{version},3.3}'`-style guards or an install-time version probe). `doctor` warns on 3.2, fails below 3.2. Real-render tests run on the installed 3.2a.
- **D-4 Packaging (replaces M9 "Builds").** GoReleaser drives releases: linux/darwin × amd64/arm64 tarballs, `.deb` and `.rpm` via nfpm, `checksums.txt`, a Homebrew formula pushed to `jmvaldez/homebrew-tap` (works on linuxbrew and macOS), and a signed apt repository published to GitHub Pages. `make release` wraps `goreleaser release --snapshot --clean` locally. The Claude Code plugin still installs from the repo as its own marketplace; packages print the plugin commands post-install, never run them. Package installs put the binary in `/usr/bin` (deb/rpm) or the brew prefix; `make install` still targets `~/.local/bin`. `doctor` must accept any of these locations.
- **D-5 resurrect/continuum.** Restored panes get new pane ids (FACTS F13), so restored agents show `? pane gone` until their next hook rebinds them. Expected behavior; documented in HANDOFF.
- **D-6 Linux notifier.** Primary Linux backend is direct D-Bus via `gdbus call --session --dest org.freedesktop.Notifications … Notify` (returns the id; `replaces_id` for replace; `CloseNotification` for retract; actions when the server advertises `actions`). `notify-send --print-id` is a fallback only when its version is ≥ 0.8. Ids parsed with a regex on `uint32 (\d+)`. Ids persisted in `notify.json`. (FACTS-CHECK change 1)
- **D-7 needs-you exit via agents.json.** Exception to "hooks win": if a live session is `needs-you` and `agents.json` (fresher than the needs-you edge) shows it with `status != waiting` on two consecutive evaluator reads, it leaves needs-you for `idle`. Covers an interactive "No" at a permission prompt, which fires no hook. (change 2)
- **D-8 Background subagent turns.** A `UserPromptSubmit` arriving while the previous `Stop` had running background tasks continues the same turn (edit count and turn start carry forward). Prompt numbering in spend comes from transcript user lines, excluding `turnOrigin == "task_notification"` / `promptSource == "system"`. (change 3)
- **D-9 Idempotent client-attached hook.** Use a fixed index `set-hook -g 'client-attached[42]' …` instead of `-ag`; verified on 3.2a in M1b (sourcing twice yields one entry). (change 4)
- **D-10 Non-interactive sessions never notify needs-you.** Hook env allowlist adds `CLAUDE_CODE_ENTRYPOINT`; record it on `SessionStart`. A session whose entrypoint is not interactive (`sdk-*`, or unknown with no status line ever seen) gets no needs-you notice; state still tracks. Capture the actual `-p` value in M1a. (change 5)
- **D-11 agents.json background rows.** Rows without `pid` (`kind: background`) key liveness on `sessionId` + `state`; the idle-over-stale-working rule and `kill -0` don't apply to them. Never use `kind` to detect `-p`. (change 6)
- **D-12 Smaller facts.** Decoder drop list and `TestPromptFilter` sentinels include every text path in FACTS-CHECK F3. Transcript scanner max line ≥ 4 MiB. Ingest skips non-message line types (`api-request*`, `atis-latch`, `mode`, `permission-mode`, `ai-title`, `last-prompt`, `queue-operation`, `attachment`). `launch_session_id` falls back to `sessionId` when snake-case `session_id` is absent.
- **D-13 First iteration scope.** Goal: bosun running on this machine end to end. Order: M1a, M1b, M2, M3 (Linux backends), M4. Then a local install (`make install`, plugin via `--plugin-dir`/local marketplace, printed statusLine and tmux edits for the owner to apply). M5, M6, packaging (D-4) and macOS/WSL follow.
- **D-14 No commits yet, so no worktrees.** Kit rule "no commits until I ask" means there is no base commit for worktree isolation; milestones run sequentially with exactly one writer in the main checkout.
- **D-15 Status line wrapping.** `bosun install` wraps any non-plain `statusLine.command` as `sh -c '<quoted>'` in both branches of the guarded form (accepted from M1a).
- **D-16 Task re-derivation.** M2 ingest re-derives the task with the configured `task.key_regex` for sessions whose `task_source` is `branch`. `tag` and `env` sources are never re-derived.
- **D-17 agents.json-only sessions.** Sessions seen only in `agents.json` (no hook activity, e.g. weeks-old `kind: background, state: blocked` rows) never appear in counts, markers, or the queue. Only hook-known sessions are tracked; `agents.json` reconciles them (liveness, status, waitingFor).
- **D-18 Claude auto-update.** Claude Code updates itself in place (2.1.309 to 2.1.310 during M1a). Demo checks compare `readlink ~/.local/bin/claude` only within one demo run.
- **D-19 Ingest order (replaces "mtime ascending", SPEC section 4).** A fork repeats its parent's rows and the first writer owns each row, so the parent must ingest first. Modification time fails when the parent keeps going after the fork (found with a real `--fork-session` capture: the fork ingested first and the parent was recorded as its child). Files are ordered by their earliest timestamp, then mtime, then path. A file that repeats rows owned by another session is a fork of that owner; `forked_from` is set from that, with no uuid or startTime heuristics.
- **D-20 Session totals.** Running with a status line snapshot: snapshot total plus banked. Otherwise a `cost-state` total (last line per `startTime` group, summed), plus only the part of snapshot total plus banked that exceeds it (a `/login` reset cost-state missed), never both. No snapshot or cost-state: the priced rows, marked `est.`. A fork's inherited spend is, in order: the status line's first total for the fork (taken before it spends), the parent's gross total if the parent did nothing after the fork, else the priced parent rows up to the fork point.
- **D-21 Resumed-session gap.** A session's trusted total is the sum of the last `cost-state` per `startTime` group (as specified) plus the transcript estimate of rows timestamped before the earliest `startTime` (a process that never wrote `cost-state`). That part is stored in `total_usd`, marked `est.`, and counts toward the estimated share (`sessions.covered_from` records the boundary). Rows after the earliest `startTime` stay covered by Claude's figure.
- **D-22 Linux click.** A posted notice that carries a session also carries a default action ("Open in tmux") when the server advertises `actions` (probed once a day, cached in `notify.json`). The dispatcher spawns `bosun notify-click`, a detached child that runs `gdbus monitor --session --dest org.freedesktop.Notifications` with a hard 2 minute deadline and runs `bosun jump --session` on the matching `ActionInvoked`. It ends on a click, on `NotificationClosed`, or at the deadline. No daemon: one bounded child per clickable notice. GNOME Shell does not emit `NotificationClosed` for a client-initiated close, so a retracted notice's listener lives out its 2 minutes.
- **D-23 Version stamping.** Release builds are stamped with `-X main.version`. Unstamped builds report `<VERSION>-dev+<vcs.revision[:7]>`, or `<VERSION>-dev` without VCS info. The plugin manifests always carry `VERSION`; doctor compares by major.minor.
- **D-24 Retention.** Request rows past 400 days are folded into `rollups` (per session, UTC day, model) priced at roll-up time and shown as rows in every spend view; sessions, subagents and rollups are kept forever. Session dirs are pruned seven days after the session ended and a later full ingest.
- **D-25 Doctor is read-only and runs no catch-up evaluation**, which would write `live.json`. It is the one user-facing command outside the catch-up rule.
- **D-26 `--apply` edits the user's files (overrides kit SPEC/PROMPT "bosun never edits your files", for these two commands only).** The owner found the manual steps too many. `bosun install --apply` and `bosun uninstall --apply` make the plugin, status line and tmux steps themselves; plain `install` and `uninstall` still print. Each run prints a plan (before and after for the status line command, the tmux line and its position), asks `Apply these changes? [y/N]` once, and `--yes` skips the prompt; non-TTY stdin without `--yes` refuses and changes nothing. Steps are idempotent and say "already done". Every file is copied to `<file>.bak-bosun-<timestamp>` before it is written and the path is printed. Details: (1) plugin: `claude plugin marketplace add <dir>` (repo, the share dir next to the binary, or /usr/share/bosun) then `claude plugin install bosun@bosun`, skipped when settings.json enables it exactly once. (2) status line: `statusLine.command` is replaced by the same `WrapCommand` string `install` prints; settings.json is edited as text so key order, indent and unknown keys survive byte for byte; with no statusLine, bosun adds `{"type":"command","command":"<wrapper around nothing>"}`, which captures spend and shows nothing; invalid JSON refuses the step. (3) tmux: the file tmux reads (`~/.tmux.conf`, `$XDG_CONFIG_HOME/tmux/tmux.conf`, `~/.config/tmux/tmux.conf`; `~/.tmux.conf` is created when none exists), the `source-file -q` line goes right after the tpm `run` line, else at the end, then `tmux source-file` runs if a server answers. (4) the run ends with the doctor checks. Uninstall reverses each step (a statusLine bosun added is removed; otherwise the original command is restored; exactly the one source-file line is removed). `--purge` semantics are unchanged. Uninstall also, when a tmux server answers, unbinds the prefix keys the generated conf bound (only those still bound to a bosun command) and unsets `client-attached[42]` (only if it holds a bosun command), since re-sourcing cannot remove them. `--purge`/`--purge-config` are plan steps and run only after the yes; a refused or declined confirmation changes nothing.
- **D-27 Text may be shown, never stored (overrides the kit privacy rules on this point only).** Prompt text, question text and tool commands may be SHOWN in the status popup, the spend view and notices. They are read from the transcript at render or notify time only (as `v` peek does) and dropped after the frame or the notice. They are NEVER written to bosun state, logs, the ledger, live.json, notify.json, alerts or exports. The hook decoders are unchanged: event lines still never contain text (`TestPromptFilter`). `[privacy] show_text = true` (default) enables the display; `false` restores the enum-only display and enum-only notices. Notify-time text is read by the detached dispatcher from the transcript, so it never travels in a command line or a file. Visual overhaul (the owner's mockups in `build-log/mockups/`): the default bar is labeled colored blocks (`⚑ 2 waiting`, `▲ 1 runaway`, `✓ 1 done`, spend, counts) and `bar.style = "compact"` keeps the terse form; `ui.glyphs = "ascii"` swaps ⚑ ▲ ✓ for ! ^ +; `quiet` is its own display state (purple, after working) instead of a runaway; prefix+W is the status view and prefix+$ (`tmux.spend_key`, overriding tmux's rename-session default) the spend view; notices use `<i>` for the second line, not `<span>`, because GNOME Shell escapes any markup but b, i, u and a.
- **D-28 Unattributed spend is apportioned, not booked on one day.** A session's status-line total can exceed its priced rows by real money: Claude bills subagent work that subagent transcripts do not record (most subagent messages lack the final usage line, and some subagent-model requests are never logged). Booking the whole remainder at the session's last activity put money from earlier days on today. `spend.Contributions` now splits the remainder over the session's (day, model, agent) buckets in proportion to its subagent rows' USD, or all its rows when it has no subagent, each part stamped on its own bucket's day and marked est.; real rows are never scaled and the parts sum to the remainder exactly. A session with no rows keeps one remainder on its last activity day. `spend --by model` and the popup's BY MODEL fold the parts into their model (est.), `--by subagent` and the subagent share include them, and `unattributed` survives only where there is nothing to apportion by. `Contributions` takes an optional clock (UTC by default) because a day is the clock's. Not done: recording the status-line total at each day boundary (a spend_samples table) so a day could be placed by Claude's own figure; apportioning is the fallback it would sit in front of.
- **D-29 Stdin deadline and dispatch order (corrects kit LESSONS L-17 and SPEC section 6 Flow).** (1) L-17 names `SetReadDeadline` plus `io.LimitReader`; a blocking pipe cannot take a read deadline, so `internal/stdin` reads in a goroutine that is abandoned on timeout (the hook process exits right after) and caps the bytes it keeps at the limit. The rule and its test (never-closing stdin returns in under 300 ms, exit 0) are unchanged. (2) The Flow bullet lists render after rate-limit; `notify.Dispatch` renders right after the edge re-check and before the focus check, dedupe and rate-limit, so a request that cannot render is dropped before it can suppress, dedupe or spend a rate-limit slot. Order in code: lock, re-check edge, render, focus (attention kinds only), dedupe, rate-limit, post. Other kit statements already superseded elsewhere in this file: ingest order (D-19), "never edits your files" (D-26), the unattributed remainder (D-28), the catch-up hook `client-attached[42]` instead of `-ag` (D-9).
- **D-30 Jump queue follows the displayed state (amends SPEC section 7, Jump).** SPEC says "Runaway, working, idle are never targets". A needs-you session that also carries a runaway alert displays as needs-you everywhere (`live.Session.Display`: needs-you hides any alert), so `live.Queue` keeps it as a target; skipping it left prefix+a unable to reach a session that is visibly waiting. A done session with a runaway alert displays as runaway and stays out of the queue. "Runaway" in that SPEC line means the displayed state, not the alert flag.
- **D-31 First-run `bosun setup`; live cost is opt-in (amends D-26).** Install is `brew install jmvaldez/tap/bosun` then `bosun setup`, which asks one question, "Show live session cost?", Yes by default (arrow keys or y/n, enter, Esc or Ctrl-C aborts with no changes; `--yes` and `--no` answer for it; with no terminal and no flag it prints "run `bosun setup` in a terminal", changes nothing, and exits 2, or 0 when the plugin is already enabled). Yes wraps `statusLine.command` as before, with a backup; No unwraps it through the existing uninstall step, restoring the original. Everything else runs without a plan or a second prompt: the plugin (`claude plugin install bosun --marketplace <share dir>`, which adds the marketplace itself; `install --apply` now uses the same one command), bosun's tmux conf, then the doctor checks, of which only failures are shown. Bare `bosun` on a terminal runs the flow first when the plugin is not installed. `install --apply` still works and is the plan-first route that also edits the user's tmux config. **Live cost is read from settings.json** (the statusLine is bosun's wrap), never stored; the doctor's `statusline` check is therefore OK, not FAIL, when it is unwrapped. **Redaction when off:** a session with no trusted total (`ledger.Session.Trusted` false: running without status-line data, crashed, pre-install, orphan rows) loses its dollars in `spend.Redact`: the contribution keeps its tokens, gets USD 0 and `Redacted`, so every sum leaves it out, and views draw `—`. Totals say how many sessions they leave out (`+ 2 —` in the bar, popup and `spend` text; `redacted` in today.json, `redacted_sessions` in `spend --json`; CSV is unchanged). Trusted sessions are untouched, estimated parts included. All readers go through `refresh.Contributions`, so the bar, the popup and `spend` agree; the refresher writes today.json from the redacted figures, which makes the daily budget and pace rules exact-only when off, and `session_cost` already read only status-line snapshots. The subagent cost rule stays as it was (estimate by nature, labelled est.). **No edits to the user's tmux config:** `setup` regenerates `~/.local/share/bosun/tmux.conf` and sources it into the running server; the plugin's SessionStart hook forks a detached `bosun tmux-sync` inside tmux, which regenerates the conf, reads the server's `@bosun-version` (set by the last line of the conf) and sources the conf only when it differs, so a restarted server or an upgrade is picked up by the next Claude Code session without touching the hook's budget or its exit code. **Stable paths:** os.Executable resolves into Homebrew's versioned Cellar dir, which `brew cleanup` deletes, so the binary path written into the tmux conf and the share dir given to `claude plugin install` come from the PATH location (`exec.LookPath`) when it is the same file as the running binary (`install.StablePaths`), falling back to the resolved dir. Not done: a stale `bosun` marketplace already registered at a deleted path is not repaired.
- **D-32 `install --apply` removed; `setup` is the install path (amends D-26 and D-31).** D-31 kept `install --apply` as the plan-first route. It left machines in a different state from `setup` (it always wrapped the status line and added a `source-file` line to the user's tmux config, which D-31 moved away from), and its `--show-diff` dumped an unreadable shell line, so two install paths are one too many. `bosun install --apply`, `--yes`, `--show-diff` and `-v` now exit 2 with "bosun install: --apply was removed; run `bosun setup`". Plain `bosun install` stays: it writes bosun's own files and prints the edits for people who make them by hand. `bosun uninstall` and `uninstall --apply [--yes] [--show-diff] [--purge…]` are unchanged and still remove the `source-file` line that an install made by the old route left in the user's tmux config. Removed with it: the install-only tmux step, `InstallApply`, and `doctor.Summary`. The shared step, plan and diff code stays because setup and uninstall use it.
- **D-33 Context fill from the status line.** The status line stdin carries `context_window.used_percentage` (confirmed in `testdata/statusline-stdin.json`, Claude Code 2.1.309). The wrapper records it in `statusline.json` as `ctx_pct` and `ctx_size`, as pointer fields so that a missing or null value stays unknown and never reads as 0 (`Snapshot.Ctx`). The evaluator reads the snapshot once per session per tick and carries the fill in `live.json`; `status --json` reports it as `ctx_pct` (absent when unknown) and the popup shows a CTX column: `41%`, or `—` when unknown, default colour below 50%, amber from 50%, red from 70%. The column is the first to go when the popup is narrower than 90 columns, and it takes its 5 columns from STATE. `bosun doctor` gains `context-field`: OK when one of the 5 most recently modified snapshots has the field, a warning when every sampled snapshot from Claude Code 2.1.309 or later lacks it (handoff suggestions would never fire), OK with "no status line data yet" when there are none. No text is involved, so D-27 is unaffected.
- **D-34 Handoff suggestion is advisory, not runaway.** When a session's context fill (D-33) reaches `handoff.suggest_at` (default 0.70; `0` turns it off) and the session is `done` or `idle`, the evaluator raises a `handoff` alert, scoped to the session with the detail `ctx 78%` (an enum and a number, so D-27 is unaffected). It goes through the same `Reconcile` as the other rules, so it fires once, clears when the fill drops (`/compact`) or the session starts working, and re-arms after that. `markRunaway` handles it like `quiet`: it sets `Session.HandoffSuggested` and never `Runaway`, so it does not count as a runaway and does not remove a done session from the jump queue (`live.Queue` checks the state, not the display). Display precedence becomes needs-you > runaway > handoff > done > working > quiet > idle: a runaway alert on the same session wins, and needs-you hides both. The bar shows `⇄ N handoff` (cyan), the popup row `⇄ handoff · context 78% · consider a handoff` (no key hint until the handoff command exists), the tab marker `⇄` (`<>` with ascii glyphs), and a `Handoff suggested` desktop notice follows the existing rules for alert notices (retracted when the alert clears). Config keys `handoff.suggest_at`, `handoff.prompt`, `handoff.dir`, `handoff.deadline` and `handoff.auto` are registered now; only `suggest_at` has an effect yet. The rule also skips a session whose `handoff.json` phase is `writing`, `launching` or `done`; the file does not exist until the command lands.
