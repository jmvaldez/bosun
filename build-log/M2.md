### Real-data runs

- `bosun spend` over this machine's history (temp `BOSUN_*_DIR`, real transcripts read-only): first ingest of 104 files / about 9.6k request lines took 0.89 s; the second run 0.04 s.
- **Live fork capture** (private tmux server, `claude -p --model haiku`: new, `--resume`, `--resume --fork-session`, then `--resume` the parent again). Claude Code's own totals: parent after the fork point `0.00474228`, fork `0.00513642`, parent final `0.00553132`. bosun: parent own `0.00553132`, fork gross `0.00513642`, inherited `0.00474228` (exact), fork own `0.00039414`. This run exposed a real bug in the first design (SPEC's "mtime ascending"): the parent, modified after the fork, ingested second and was recorded as the fork's child. Fixed by D-19 and covered by the updated unit test.
- **Resumed sessions can disagree with their rows.** In 8 of the 48 checked sessions the priced transcript rows differ from the per-model `costUSD` in `cost-state` by more than $0.50; two of them are far above it (session `519b89a9`: rows 90.95 vs 37.97, +52.98; session `6c009f9e`: rows 24.52 vs 10.92), the other six are below it, the usual side-request undercount. Where token counts match, the price table matches Claude's cost exactly (`claude-opus-5`, `claude-opus-5-5`: identical to the cent). The large positive gaps are sessions whose only `cost-state` `startTime` is hours after their first line, i.e. resumed; that group's total does not cover the earlier process's spend. bosun follows the spec (Claude's figure is the session total; rows are breakdown only), so those sessions get a large negative `unattributed`. Worth deciding in review whether pre-`startTime` rows of such sessions should be added back.

## Pricing facts that shaped the table

From the pricing page (fetched 2026-10-23), all in `internal/prices`:
- Haiku 5.5 is the only tiered model: prompts over 100,000 tokens (input + cache read + cache writes) pay `$0.50 / $2.50` instead of `$0.10 / $0.50`, with cache rates scaled the same way.
- Cache read multipliers differ by model: 0.05x on Opus 5.5 and Sonnet 5.5, 0.1x on Opus 5, Sonnet 5 and older, 0.025x on Fable 5.1 and Mythos 5.1. The table stores the dollar rates, not multipliers.
- Fast mode (Opus 5.5, Opus 5, Opus 4.8) is 2x on every category; `usage.speed` carries it. `inference_geo: "us"` is 1.1x. Web search is `$0.01` per search. Pricing for the models Claude Code lists as `opus`/`sonnet`/`haiku` aliases is never needed; those appear only on non-assistant lines.
- Unknown models are priced at Sonnet 4.x rates and marked estimated.

## Judgment calls

1. **Prices stored as tokens, priced at read.** The ledger keeps token counts; `PriceRequest` prices at query time, so a corrected table fixes history without re-ingest, and there is one pricing path.
2. **Untrusted sessions have no `unattributed`.** Their total is their rows; the stored total of an estimate can lag the rows, so views use the rows.
3. **Only the session that wrote a request owns it**, enforced by `ON CONFLICT ... WHERE requests.session_id = excluded.session_id`; a conflict from another session is the fork signal.
4. **`ended_at`** is the last `SessionEnd` after the last `SessionStart`, else the last activity once `live.json` no longer lists the session as running.
5. **Refresher cost.** Each tick loads all request rows to total today. A whole second `spend` run over about 10k rows took 40 ms; if the ledger grows by 10x, `today.json` should move to an incremental query.
6. **Binary size and hook start.** Linking SQLite into the single binary raised a full-process hook run from about 2 ms to a worst case of 9.9 ms in 20 runs (still well under the 50 ms budget). The in-process p95 is unchanged (214 us).
7. **`spend` ingests first**, under `ingest.lock`; if a refresher ingest holds it, `spend` prints a note and reads what is stored. Every `--by` is implemented; an unknown one exits 2.
8. **The segment reads `today.json`**, never the ledger. A file written for another day reads as zero, so yesterday's total cannot linger.
9. **Pace and alert styles.** The segment already renders amber and red; the pace rule that selects them is M3.
