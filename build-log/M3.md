### Live gdbus check (3 real notices, all closed)

`bosun notify --test` twice, then `notify-dispatch --retract` (private state dirs, `TMUX` unset to a dead socket):

```
posted via gdbus: notifications work        notify.json: {"bosun.test":{"id":12,...}}
posted via gdbus: notifications work        notify.json: {"bosun.test":{"id":12,...}}   <- replaces_id returned the same id
retracted: bosun.test                       notify.json: {}
```

Two bugs this found, both fixed with tests: gdbus parsed the `-1` expire timeout as an option (every post failed with a usage error until `--` was added before the positional arguments), and the notify-send fallback now only claims replace and retract on libnotify 0.8 and up. The FACTS-CHECK "replaces_id not validly tested" item is closed: the server returns the same id.

### Live hook-forked dispatch with Claude Code

In a private tmux server (3.2a, themepack, attached client), a real haiku session was driven through `claude --plugin-dir ./plugin`. The hook forked the dispatcher for the permission prompt and it correctly did **not** post, because the attached client reported `focused` on that pane (Suppressed, observed as an empty `notify.json` posted map). A manual dispatch against a dead `TMUX` socket (focus Unknown) posted notice 13, which I then retracted. The session then hit the account's usage limit ("Usage limit reached, limit resets 6:40pm"), after which Claude Code fired `StopFailure`; the hook-forked dispatcher posted a "turn failed" notice (second entry in `notify.json`'s window), and the evaluator's retract removed it. That run exposed a real bug: a needs-you to done/failed move retracted the notice the new state had just posted, because both share the `bosun.<session>.attn` group. Fixed: retract only when leaving the attention states entirely, and a done notice dropped for a short turn retracts the stale needs-you one itself (`TestNeedsYouAndDoneRetractWhenTheyClear`, `TestShortDoneRetractsTheStaleNeedsYouNotice`).

The usage limit is the owner's real plan limit; see the report for what it means for further live runs.

## Judgment calls

1. **Display state.** `runaway` is a display state computed from `alerts.json`, not an attention state. Counts, markers and the popup use it; `live.Session.State` stays the attention state. Runaway sits between needs-you and done and removes a session from the jump queue.
2. **Which alerts are runaways.** Subagent, quiet and session_cost alerts carry a session and make it runaway. `daily_pace` and `daily_budget` are account-level: they notify and tint the spend, but add no `$!` pill.
3. **quiet** means: working, no tool open (`ToolOpen`), no pending background work, no running subagent, and no event for `rules.quiet`. A long single tool call and a subagent doing the work are not quiet.
4. **session_cost** reads the status line snapshot through `ledger.OwnUSD` (banked included, a fork's first total subtracted), so unwrapped sessions never trip it.
5. **Sticky per-day alerts.** Pace and budget alerts are held until the day rolls over, so a ratio hovering at its threshold cannot notify twice.
6. **Hook only hints.** The hook cannot run the state machine; it forks on events that can start a notice, and the dispatcher re-folds the session's `events.jsonl` (without writing `live.json`) and drops anything that no longer holds. The waiting episode, not the event time, is the dedupe edge. `done` values (edits, turn length, own spend) are computed by the dispatcher; the `$ this session` clause is left out when there is no status line total rather than printing a made-up figure.
7. **Linux click-through** is not implemented: it needs a process listening for the `ActionInvoked` signal, which would be a daemon. `Capabilities.Click` is false.
8. **Sound** is the freedesktop `sound-name` hint `message-new-instant` for needs-you and failed when `notify.sound` is non-empty.
9. **No test can post a real notice.** Every isolated test config sets `notify.backend = "off"`.

## Addendum: Linux click (D-22)

Built without a daemon: when a notice carries a session and the notification server advertises `actions`, the dispatcher posts it with a default action and spawns `bosun notify-click --id N --session S`. That child streams `gdbus monitor --session --dest org.freedesktop.Notifications` (a new `runner.Streamer`, with a hard deadline) and, on `ActionInvoked (uint32 N, 'default')`, runs `bosun jump --session S`; it exits on a click, on `NotificationClosed`, or after 2 minutes.

| Check | Result | Evidence |
|---|---|---|
| The post carries the action only when the server advertises `actions`, and only for notices with a session | PASS | `TestPostOffersAClickOnlyWhenTheServerAdvertisesActions`, `TestNoClickWithoutActionsOrASession`; the capability probe is cached (second dispatch does not ask) |
| The listener jumps on the default action for its own notice id, ignores other ids and other actions, and ends on close or deadline | PASS | `TestListenJumpsOnTheDefaultActionForItsNotice`, `TestListenEndsWhenTheNoticeIsClosedOrTimesOut` (canned `gdbus monitor` lines); `TestStreamStopsEarlyAndKillsTheChild`, `TestStreamHonorsTheDeadline` |
| Live: a real notice with the action is accepted by this GNOME Shell, and the listener starts, streams, and is bounded | PASS | a real notice with `['default', 'Open in tmux']` was posted and closed; `bosun notify-click` ran `gdbus monitor` and stayed bounded |
| Live: a physical click on the banner reaches the listener and switches the pane | **BLOCKED** (needs a human click) | See below |
| `NotificationClosed` ends the listener | **Not observable here** | GNOME Shell (this machine) emits no `NotificationClosed` for `CloseNotification` (checked with `dbus-monitor`); the 2 minute deadline bounds it instead |

To test a click by hand (inside the demo, away from the agent window):

```sh

# switch to the shell window, wait for the banner ("waiting on you"), click it:
# the demo's tmux client should switch to the ABC-1 window.

```
